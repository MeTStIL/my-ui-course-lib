# Руководство для AI-агентов (AGENTS.md)

Этот документ описывает правила, архитектурные стандарты, стек и соглашения для разработки компонентов в проекте **MeTStIL Design System**. Все агенты, работающие с репозиторием, должны строго следовать этим инструкциям.

---

## 1. О проекте и философии

- **Тип проекта:** Учебный проект-эксперимент по созданию собственной дизайн-системы с нуля.
- **Публикация:** Не публикуется в npm-реестр (разрабатывается локально для обучения и портфолио).
- **Подход к коду:** Максимум самостоятельной реализации (self-made). Сторонние тяжелые библиотеки компонентов не используются.
- **Документация и витрина:**
  - Текущая витрина: интерактивная матрица состояний и пропсов в [`src/App.tsx`](src/App.tsx).
  - В будущем: планируется интеграция **Storybook**.

---

## 2. Протокол работы с запросами пользователя (Prompt & Planning Protocol)

Агент **никогда не начинает писать код сразу** после первого запроса пользователя. Работа строится по строгому 4-этапному циклу:

1. **Исследование контекста (Discovery & Analysis):**
   - Тщательно изучить текущую кодовую базу, архитектуру затронутых файлов, стили, типы и существующие паттерны.
   - Определить границы задачи и влияние изменений на соседние модули.
2. **Вопросы и угловые кейсы (Clarification & Edge Cases):**
   - Задать пользователю уточняющие вопросы по реализации, интерфейсам (API компонентов), краевым кейсам (edge cases), интерактивным состояниям (`:hover`, `:active`, `:focus-visible`, `disabled`) и A11y.
3. **Согласование пошагового плана (Planning & Alignment):**
   - Предложить прозрачный пошаговый план изменений: список создаваемых/редактируемых файлов, новые типы, маппинги, стили и демонстрацию в витрине.
4. **Ожидание прямого одобрения (Explicit Approval):**
   - Приступать к созданию файлов, модификации кода или установке пакетов **только после прямого подтверждения** плана пользователем («делай», «ок», «погнали», «согласовано»).
   - Если пользователь корректирует требования, обновить план и дождаться финального аппрува.

## 3. Технологический стек

- **Фреймворк:** React 19 (`react`, `react-dom`).
- **Сборщик и компилятор:**
  - Vite 8.
  - **React Compiler** (`babel-plugin-react-compiler`, `@rolldown/plugin-babel`). Ручная мемоизация (`useMemo`, `useCallback`) в большинстве случаев не требуется, компилятор оптимизирует рендеры автоматически.
- **Язык и типизация:** TypeScript (цель `es2023`, строгие флаги `verbatimModuleSyntax: true` и `erasableSyntaxOnly: true`).
- **Стилизация:**
  - Переход на **Vanilla Extract** (`@vanilla-extract/css`) — zero-runtime, типобезопасные CSS-in-TS стили и дизайн-токены.
  - Исторически использовался SCSS Modules (`*.module.scss`), который подлежит замене на Vanilla Extract.
  - Утилита для классов: `clsx`.
- **Линтинг и кодстайл:**
  - ESLint 9+ (Flat config) с жесткими правилами для импортов, JSX и типизации.
  - Prettier.

## 4. Архитектура компонентов (Golden Standard)

Каждый компонент изолируется в отдельной папке внутри `src/components/<component-name>/` и состоит из 4 обязательных файлов:

```text
src/components/<component-name>/
├── <ComponentName>.tsx       # Реализация компонента
├── interface.ts              # Типы, интерфейсы и константы пропсов
├── <ComponentName>.css.ts    # Стили (Vanilla Extract)
└── index.ts                  # Точка публичного реэкспорта компонента
```

### 3.1. Соглашения по типам (`interface.ts`)
- Все типы именуются с префиксом `T` (например: `TButtonProps`, `TButtonSize`, `TButtonVariant`, `TAllowedButtonTags`), а интерфейсы с префиксом I.
- Для полиморфных компонентов:
  - Тип допустимых тегов: `export type TAllowed<Name>Tags = 'button' | 'a';`
  - Пропсы наследуются от `ComponentPropsWithRef<T>`:
    ```typescript
    import type { ComponentPropsWithRef } from 'react';

    export type TComponentProps<T extends TAllowedTags = 'div'> = ComponentPropsWithRef<T> & {
      as?: T;
      variant?: TComponentVariant;
      size?: TComponentSize;
    };
    ```
- Документировать JSDoc-комментариями назначение пропсов и значения по умолчанию (`@default`).

### 3.2. Соглашения по реализации (`<ComponentName>.tsx`)
- Явный возвращаемый тип: функции компонентов должны явно возвращать `ReactElement`.
- Полиморфный тег: `const Tag = (as ?? 'defaultTag') as ElementType;`
- Маппинг вариантов и размеров: выносить маппинги классов в отдельные `Record`-объекты:
  ```typescript
  const SIZE_MAP: Record<TComponentSize, string> = { ... };
  const VARIANT_MAP: Record<TComponentVariant, string> = { ... };
  ```
- Обязательно указывать `displayName`:
  ```typescript
  ComponentName.displayName = 'ComponentName';
  ```
- Поддержка доступности (A11y): всегда прокидывать `aria-*` атрибуты (например, `aria-disabled={disabled}` при `disabled`).

### 3.3. Экспорты (`index.ts`)
- Внутри папки компонента `index.ts`:
  ```typescript
  export { ComponentName } from './ComponentName';
  export type * from './interface';
  ```
- Централизованный экспорт: каждый новый компонент **обязательно** экспортируется наружу через [`src/components/index.ts`](src/components/index.ts).

## 5. Правила кодстайла и линтинга (ESLint & TypeScript)

В проекте настроены строгие правила, за нарушение которых `npm run lint` выдаст ошибку:

1. **Раздельные импорты типов:**
   - Запрещены совмещенные импорты типов и значений.
   - Обязательно использовать `import type { ... }` на отдельной строке (`@typescript-eslint/consistent-type-imports`).
2. **Сортировка импортов (`simple-import-sort`):**
   - Импорты должны идти единым монолитным блоком без пустых строк в строгом порядке:
     1. Node.js встроенные модули (`node:*`).
     2. Внешние пакеты (`react`, `clsx`).
     3. Внешние импорты типов (`import type ... from 'react'`).
     4. Абсолютные импорты и алиасы.
     5. Относительные импорты типов.
     6. Относительные импорты значений.
     7. Файлы стилей (`*.css`, `*.scss`, `*.css.ts`) — **всегда в самом низу блока**.
3. **Строковые JSX-пропы:**
   - Никаких фигурных скобок для строк: `size="M"`, а не `size={'M'}` (`react/jsx-curly-brace-presence`).
4. **Неиспользуемый код:**
   - Неиспользуемые импорты и переменные вызывают ошибку линтера.

## 6. Тестирование и Git-процессы

- **Тесты:** На текущем этапе тесты не пишутся (QA строится на визуальной проверке и линтере).
- **Git & Commits:** Агент **не делает** коммиты и не пушит в репозиторий. Управление ветками, версиями и создание коммитов пользователь выполняет самостоятельно.

---

## 7. Чеклист добавления нового компонента

При разработке или рефакторинге компонента агент должен выполнить следующие шаги:

1. **Создать структуру компонента:**
   - `src/components/<name>/interface.ts` (типы с префиксом `T`, пропсы, полиморфизм).
   - `src/components/<name>/<Name>.css.ts` (стилизация через Vanilla Extract).
   - `src/components/<name>/<Name>.tsx` (реализация с `displayName`, `Record`-маппингами, `ReactElement`).
   - `src/components/<name>/index.ts` (реэкспорт).
2. **Зарегистрировать в дизайн-системе:**
   - Экспортировать компонент и типы в [`src/components/index.ts`](src/components/index.ts).
3. **Обновить витрину:**
   - Добавить секцию с демонстрацией вариантов, размеров и состояний в [`src/App.tsx`](src/App.tsx).
4. **Обязательная валидация (выполнить команды в терминале):**
   - `npm run lint` — проверка ESLint и сортировки импортов (должно быть 0 ошибок).
   - `npm run build` — проверка типов TypeScript (`tsc -b`) и сборки Vite (должно успешно собраться).
